The question everyone asks

“How does a sentence become a simulation?”

Short answer: the LLM never writes the solver’s input. It fills in a short, documented description of the problem. Ordinary code does everything after that, and checks the result.

Step 1 · The LLM

Intent becomes a study

“What’s the pressure drop of water through a 20 mm pipe at 2 L/min?”

The model first calls study_format: the vocabulary, units, conventions, an example, and what this machine can run.

The study is in the user’s terms. No mesh, no node numbers, no solver files.

{

"pipe_dp": {

"geometry": {"cylinder": {"d": 20, "l": 400}},

"fluid": "water", "model": "laminar",

"bcs": [

{"kind": "inlet", "faces": {"nz": -1}, "flow": 3.33e-5},

{"kind": "outlet", "faces": {"nz": 1}, "p": 0}

]

}

}

Simplified; key names illustrative. Units: mm, m³/s, Pa. Faces are chosen by direction, not by number.

Step 2 · Code

Validation: errors that say the fix

Static checks before anything is computed. The model reads the messages, fixes the study, and tries again.

Error

bcs[0].faces {nz: 1}: took the outlet end; the inlet is at z = 0: use {nz: -1}

Error

run.mem 200G: at most 96G on this machine; choose a machine with more, or ask for less

Warning

mesh.size not given: the default (1/30 of the domain diagonal) is coarse; give one

Examples of the kind of messages validation returns.

Step 3 · Code

The translation itself is ordinary code

01

Geometry and mesh

Built from a CAD description or a STEP file, then meshed with our own numbering.

02

Boundary conditions

Placed by geometric rules; the result reports which faces each condition took.

03

Physics bookkeeping

Properties, unit conversions, coefficients and solver settings, from tested code.

04

Solver input

OpenFOAM case, CalculiX deck, LAMMPS script or Modelica model, written by us, then run.

No LLM here: the same study always gives the same files, and every file can be inspected.

Step 4 · Code

Every run checks itself

Invariants

Mass, momentum and energy balances; force equilibrium. On every run.

Reference

An independent solver recomputes what it can, to catch translation errors.

Benchmarks

Closed-form and published answers, each with a stated tolerance.

Expected values

The study can state what it expects; each is checked after the run.

reliable: true

reliable: false

With the reasons. The model is told not to report numbers from an unreliable run.

An analogy that lands

It works like a compiler

CompilerTranslator
Source codeThe user’s request
Front end: parse to an intermediate formThe LLM writes the study
Type checkerValidation
Back end: generate machine codeThe translator writes the solver input
Test suiteThe checks on every run

The study is the intermediate form: small enough for a model to write, exact enough for code to compile.

Why split it this way

Each side does what it is reliable at

LLMs are good at

  • Understanding what the user means
  • Choosing the right analysis
  • Filling in a structured form
  • Reading results and explaining them

Code is good at

  • Consistent numbering and bookkeeping
  • Units and thousands of coefficients
  • Doing the same thing every time
  • Checking conservation laws exactly

Every run is reproducible and auditable: the study and the generated inputs are saved.

Putting it together

One request, end to end

You ask

“What’s the pressure drop of water through a 20 mm pipe at 2 L/min?”

The LLM writes

A study of about 20 lines: a cylinder, water, an inlet and an outlet named by direction

Validation

Clean, or errors with fixes; the LLM corrects the study and resubmits

The translator

Meshes the pipe, applies the conditions, writes and runs the OpenFOAM case

You get

Δp in Pa · the mass balance · reliable: true, explained in words
